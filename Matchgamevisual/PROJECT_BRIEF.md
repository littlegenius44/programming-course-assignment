# MatchLab — Web 消消乐算法可视化游戏

## 1. 项目定位

### 1.1 项目背景

本项目源于大学 C/C++ 程序设计课程的“改版消消乐游戏”课程设计。

原始任务要求通过二维数组实现消消乐游戏，包括随机初始化、连续匹配检测、物品消除、重力下落、随机补充、连锁消除、计分和胜利判定。

目前已经完成一个基于 C 语言的 Windows 控制台版本，采用 `main.c`、`game.c`、`game.h` 的模块化结构，并实现了基础游戏规则、计时和关卡功能。

课程允许使用其他编程语言完成扩展版本，并将其作为加分项。因此计划重新开发一个 Web 图形版本。

### 1.2 核心定位

**一个以消消乐游戏为载体、以算法可视化和交互展示为核心的轻量级 Web 项目。**

本项目不是商业化消消乐游戏，也不是功能庞杂的游戏平台。

主要目标有三个：

1. **算法正确性**：完整实现原题的消除规则，确保游戏逻辑可靠。
2. **算法可视化**：清晰展现交换、匹配检测、统一消除、重力下落、随机补充以及连锁消除的过程。
3. **交互与视觉质量**：利用现代 Web 技术制作视觉精致、操作直观、动画流畅的游戏界面，形成具有展示价值的课程设计作品。

项目质量重点是算法设计、模块组织、动态效果和整体完成度，而不是功能数量。

### 1.3 开发原则

- 优先保证算法正确，再完善视觉表现。
- 以课程题目为约束，不为了视觉效果改变基础规则。
- 保持游戏逻辑与图形渲染解耦。
- 注重程序结构清晰、模块职责明确、代码可维护。
- 避免过度设计，不为未来不确定的功能提前搭建复杂系统。
- 采用逐阶段开发，每个阶段形成可运行、可验证的成果。
- 允许重构已有 C 语言算法，不要求复用原始 C 代码。
- 优先实现能够直观展示算法价值的功能。

**C. 页面与交互层（UI）**

负责：

- 开始页面
- 玩家昵称与规则设置
- 分数、时间、关卡信息
- 游戏说明
- 暂停与重新开始
- 游戏结果展示

三层之间通过明确的数据接口进行交互，不允许渲染层重复实现核心游戏规则。

## 3. 游戏规则与功能边界

### 3.1 棋盘基础规格

严格保留原题要求：

- 棋盘：30 列 × 20 行。
- 物品类型：9 种，分别对应数字 1～9。
- 消除长度：当前支持 `k=3`、`k=4`；用户确认本轮不开放 `k=5`。
- 玩家操作：交换相邻两个物品。
- 仅当交换能够形成有效消除时保留交换，否则恢复原状。
- 横向或纵向连续不少于 k 个相同物品时，消除整段。

### 3.2 棋盘初始化

初始化时随机生成物品，不得出现已经满足消除条件的连续组合，并保证至少存在一个有效相邻交换。新局、换关和自动洗牌共用此规则。

建议采用逐格约束生成：

- 按行列顺序填充。
- 对当前候选数字检查左侧和上方连续数量。
- 从不会形成消除的候选数字中选择，避免异常随机源导致无限重试。

可玩生成最多尝试三张随机棋盘；均无操作时，在初始化过程中植入两行保证一次有效交换的图案，再按原有约束填充并验证。正常消除后的随机补充仍允许连锁。

### 3.3 消除与连锁

一次有效交换后的处理流程：

1. 找到全部横向、纵向匹配段。
2. 使用独立标记数组统一记录待消除位置。
3. 横纵交叉位置只计算一次。
4. 清除全部已标记物品。
5. 按列模拟重力，将剩余物品向下压缩。
6. 在顶部随机生成新物品。
7. 检测是否产生新的匹配。
8. 重复直到棋盘稳定。

同一次有效交换中的连锁按轮次计分：第 1 轮每格 10 分，第 2 轮每格 20 分，第 3 轮及以后每格 30 分。每轮得分为去重后的消除格数乘以该轮每格分值，下一次交换重新从第 1 轮计分。

第 2 轮及后续连锁可播放轻量爆炸效果，增强连续得分的反馈。爆炸属于视觉效果，不额外消除周围格子，也不改变匹配、下落或补充规则。首版先实现上述固定规则，其他变化另行设计。

### 3.4 计时、关卡与胜利

保留已有 C 版本的规则：

| 关卡 | 目标累计分数 |
|---|---|
| 第一关 | 300 |
| 第二关 | 700 |
| 第三关 | 1200 |

达到 300、700 分后进入下一关，并重新生成棋盘；达到 1200 分后判定整局胜利。

切换关卡时保留累计分数、玩家昵称、消除长度和累计时间。

一次有效操作产生的所有连锁消除应结算完成后再检查关卡或胜利。

游戏计时采用整局累计用时，不设置强制倒计时。

主动暂停及切到后台停止计时和动画，返回后等待玩家主动继续；正常操作、提示检测、洗牌与动画期间累计用时。

### 3.5 可用操作、自动洗牌与免费提示

本节是用户后续确认的规则扩展，已于2026-10-13实施：

- 稳定棋盘按行优先枚举向右、向下相邻交换，在副本上临时交换、检查匹配并恢复。
- 无可用操作时显示“当前无可用操作，正在重新生成棋盘”，锁定输入，重新生成并验证可玩棋盘。
- 自动洗牌保留昵称、消除长度、累计分数、关卡、用时和演示偏好，不产生消除或额外得分。
- 已完成回合先提交，再播放独立SHUFFLE步骤。洗牌期间退出或失败仍保留该回合成绩；失败暂停并提供重开与退出。
- 按H或点击“提示（H）”给出一组有效操作的1基坐标、方向和两格高亮。提示免费、不限次数，不执行交换、消除或计分，不消费随机数。
- 动画、洗牌、暂停、结束或故障时禁用提示；输入文字和操作选择框时保留原生键盘行为。
- 当前只推荐固定遍历顺序找到的首个操作，不计算最优得分，不增加提示次数限制或k=5。

## 4. 算法可视化设计

这是本项目区别于普通消消乐游戏的重点。

### 4.1 核心思想

**算法的实际执行过程应当能够被玩家直观地观察，而不是仅仅在屏幕上呈现最终运算结果。**

因此，不能简单地在一次调用中完成全部消除，然后直接绘制最终棋盘，并使用与真实中间状态无关的装饰动画。

建议游戏逻辑产生结构化的步骤数据，供表现层按顺序播放。

例如：

`SWAP → MATCH → CLEAR → GRAVITY → REFILL → CASCADE_CHECK → STABLE`

每一步都应具有对应的棋盘状态或变化信息。

### 4.2 重点展示内容

**交换阶段**

- 两个相邻物品平滑交换。
- 无效交换播放回退动画。
- 有效交换进入匹配阶段。

**匹配检测阶段**

- 对符合条件的连续物品进行高亮。
- 同时支持横向和纵向匹配。
- 当两组匹配发生交叉时，正确展示统一标记结果。

**消除阶段**

- 已匹配物品执行短暂闪烁、缩放或淡出。
- 消除效果清晰但不过于花哨。
- 显示本次消除的得分增量。

**重力阶段**

- 剩余物品按照其真实位置变化向下移动。
- 动画位置必须与核心算法计算结果一致。
- 同一列中的物品保持原有相对顺序。

**补充阶段**

- 新物品从棋盘顶部进入。
- 补充后可能产生新的消除。
- 若发生连锁，自动继续播放后续阶段。

**连锁阶段**

- 显示 `CHAIN ×2`、`CHAIN ×3` 等提示。
- 连锁轮次与实际算法执行一致。
- 连锁计分与轮次一致：每格 10/20/30 分，后续轮次封顶为每格 30 分。
- 爆炸效果只作用于本轮真实消除的位置，不新增消除范围。
- 动画播放期间锁定玩家操作，防止状态冲突。

### 4.3 算法演示模式

建议设计一个可以开启或关闭的“算法演示模式”，作为课程展示的特色功能。

普通模式关注游戏体验；算法演示模式关注执行过程。

在算法演示模式中：

- 使用更清晰的颜色或边框突出待消除格子。
- 显示当前执行阶段，例如“匹配检测”“统一消除”“重力下落”。
- 可以适当降低动画播放速度。
- 明确显示一次消除的格子数量及得分。

首版只需实现自动分阶段演示和速度调整，不要求完整的断点调试、逐语句执行或复杂的可视化调试器。

按用户后续要求，桌面端将算法说明放在棋盘右侧。开启演示与普通模式采用相同棋盘宽高约束，不为说明栏额外缩小30×20棋盘；横向空间不足时说明换到下方。

## 5. 视觉设计定位

### 5.1 整体风格

采用现代、简洁、轻量且具有游戏感的视觉风格。

关键词：

**清晰、精致、轻快、流畅、视觉统一。**

不追求复杂商业游戏场景，而是强调：

- 清晰的棋盘布局
- 协调的色彩体系
- 高质量的交互反馈
- 适度的动画
- 突出的算法演示效果

整体可适当使用柔和阴影、圆角、渐变和轻量粒子效果，但不能降低棋盘可读性。

### 5.2 棋盘设计

由于棋盘包含 600 个格子，必须将信息密度视为重要的设计约束。

建议：

- 9 种物品对应 9 种容易区分的颜色。
- 保留数字 1～9，避免纯颜色识别带来的歧义。
- 保持明确的格子间距和边界。
- 选中物品使用醒目的描边或光效。
- 消除动画不遮挡大面积棋盘。
- 保证 30×20 棋盘在常见桌面屏幕上可完整显示。

### 5.3 页面结构

第一版只需要三个主要页面：

**开始页面**

- 游戏标题
- 玩家昵称输入
- 消除长度选择
- 开始游戏按钮
- 简要玩法介绍

**游戏主页面**

- 完整棋盘
- 当前玩家
- 累计分数
- 当前关卡
- 目标分数
- 累计时间
- 算法演示模式开关
- 暂停或退出入口

**结束页面**

- 胜利或主动退出状态
- 玩家昵称
- 最终分数
- 总用时
- 重新开始按钮

不增加不必要的多级导航和复杂页面体系。

## 6. 操作交互

首版采用“点击两个相邻格子进行交换”。

具体约定：

- 第一次点击：选中物品，显示边框。
- 第二次点击相邻位置：尝试交换。
- 第二次点击相同位置：取消选择。
- 第二次点击非相邻位置：切换选择。
- 点击棋盘外部：不执行交换。
- 动画执行期间：禁止新的交换操作。

输入层只负责将鼠标位置转换为棋盘坐标，并将操作交给核心游戏规则处理。

不应在输入层重新实现匹配算法。

## 8. 工程质量与测试要求

核心游戏逻辑应当具备独立测试能力。

建议使用固定随机种子或可注入随机数生成器，以便复现棋盘和测试结果。

重点测试：

1. 初始棋盘不会出现可直接消除的组合。
2. k=3/4 时连续匹配判断正确。
3. 超过 k 个的连续物品会整段消除。
4. 横纵交叉位置不会重复计分。
5. 无效交换能完整恢复棋盘。
6. 重力下落保持物品相对顺序。
7. 随机补充后能够继续触发连锁。
8. 连锁结束后棋盘没有待消除组合。
9. 连锁每格 10/20/30 分、每次交换重置轮次，以及关卡切换正确。
10. 图形动画不会导致游戏状态重复更新或丢失。

核心逻辑测试不应依赖浏览器画面截图才能判断结果。

代码应具有必要的函数注释、关键算法解释和清晰的类型定义，但避免对显而易见的语句进行冗余注释。

## 9. 开发路线

### 阶段 A：核心规则重建

使用 TypeScript 重建核心游戏算法。

优先保证与原 C 版的规则一致，并完成关键单元测试。

交付标准：无图形界面也可以独立执行完整的棋盘初始化、交换与连锁结算。

### 阶段 B：Web 基础游戏

使用 Phaser 实现游戏场景。

包括棋盘显示、鼠标选择、物品交换、分数、关卡和基础页面。

交付标准：浏览器中可以完成一局游戏。

### 阶段 C：动画与算法展示

加入交换、匹配、消除、下落、补充动画，建立稳定的动画播放流程。

增加基础算法演示模式。

交付标准：用户能够直观看到一次有效交换引发的完整算法过程。

### 阶段 D：视觉优化与交付

完善颜色、字体、布局、交互反馈以及窗口尺寸适配。

修复边界问题，整理文档，完成生产构建并部署静态网站。

交付标准：项目能够稳定演示，具备清晰的启动与操作说明，适合课程展示。

## 10. 对 Codex 的执行要求

本文件是项目定位与设计约束，不是要求一次性实现所有功能的编码指令。

执行时应遵循：

1. 首先检查现有项目目录。如果能访问原 C 语言版本，读取其核心代码作为规则参考；如果无法访问，不得假设已经核对过原代码。
2. 根据本文档提出简洁的项目架构和分阶段开发计划。
3. 优先实现最小可运行版本，避免提前开发不必要的系统。
4. 每个阶段完成后进行编译、运行和必要的测试。
5. 遇到技术选择时优先考虑简单、稳定、可解释的方案。
6. 不自行扩展注册、登录、云服务、复杂道具等未要求的功能。
7. 不为架构抽象而架构抽象，只有确实需要时才增加模块和依赖。
8. 核心游戏规则与图形表现必须分离。
9. 对于会影响游戏规则或项目定位的重大设计变更，应先说明理由，再进行修改。
10. 保留清晰的 README，记录运行方法、技术架构和课程核心算法。
